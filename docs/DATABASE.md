# Database

## Engine

PostgreSQL 18 (`postgres:18-alpine` locally and in tests). Access through EF Core with the Npgsql provider. One `LibraDbContext` for the whole monolith; module boundaries are enforced by code organization and by not joining across modules, not by separate databases.

## Conventions

- **Naming**: snake_case for tables, columns, indexes, and constraints (D-010) via `EFCore.NamingConventions` (`UseSnakeCaseNamingConvention`). Table names are explicit in each configuration.
- **Time**: `timestamp with time zone` for instants, stored in UTC. Property names end with `Utc` (`created_at_utc`). Code writes `DateTime` with `Kind=Utc` taken from `TimeProvider`.
- **Money**: `numeric(18,2)`. Macros: `numeric(10,2)` (bounds to be documented in Phase 5). Never floating point.
- **Currency**: `character(3)` ISO 4217 code on every money-bearing row (accounts and budgets; transactions and transfers inherit the account currency).
- **Identifiers**: `uuid` primary keys generated by the application (`Guid.CreateVersion7()` for index locality).
- **Ownership**: every user-owned table has a non-null `user_id` foreign key to `users` with cascade delete and an index that starts with `user_id`.
- **Audit**: `created_at_utc`, `updated_at_utc` on mutable entities.
- **Enums**: stored as text with a check constraint, not as integers.
- **Constraints**: invariants that can be expressed in the database are (unique normalized email, unique token hash, currency length, positive amounts, distinct transfer accounts, unique budget scope, unique client request id per user).
- **Referential rules**: rows that reference accounts or categories use `ON DELETE RESTRICT`, so a referenced account or category can never disappear underneath history; the application archives them instead. `users` cascades to everything it owns.

### recurring_occurrences

| Column | Type | Notes |
|---|---|---|
| id | uuid | pk |
| user_id | uuid | fk users cascade |
| template_id | uuid | fk recurring_transactions restrict |
| year, month | integer | check `month BETWEEN 1 AND 12` |
| due_date | date | the clamped due date as computed when the row was stored |
| status | varchar(10) | check `IN ('Recorded','Skipped')` — `Pending` is never stored |
| transaction_id | uuid | nullable; fk financial_transactions restrict; unique where not null; check `ck_recurring_occurrences_link`: `Recorded` ⇔ `transaction_id IS NOT NULL` |
| title, amount, currency_code | varchar(120), numeric(18,2), char(3) | snapshot of what was recorded |

| created_at_utc, updated_at_utc | timestamptz | |
| xmin | xid | row version |

Unique index `ix_recurring_occurrences_template_month (template_id, year, month)` is what makes a concurrent or
retried confirmation of one month resolve to the one stored row. Index `(user_id, year, month)`. The `restrict`
foreign key to the transaction is why the generic transaction delete answers 409 for a linked transaction.

| Column | Type | Notes |
|---|---|---|
| id | uuid | pk |
| user_id | uuid | fk users cascade |

| kind | varchar(10) | check `IN ('Opening','Payment')` |

debt's direction and the kind (see DOMAIN.md); the account-balance calculator groups non-reversed movements per
account in one query.

## Migrations

- Location: `src/backend/Libra.Infrastructure/Persistence/Migrations` (generated code; style analyzers are relaxed for this folder in `.editorconfig`). Run `dotnet format` once after generating a migration so line endings match the repo.
- Tool: repo-local `dotnet-ef` from `.config/dotnet-tools.json` (run `dotnet tool restore` once after cloning).
- Create:

  ```bash
  ASPNETCORE_ENVIRONMENT=Development dotnet tool run dotnet-ef migrations add <Name> --project src/backend/Libra.Infrastructure --startup-project src/backend/Libra.Api --output-dir Persistence/Migrations
  ```

- Apply explicitly:

  ```bash
  ASPNETCORE_ENVIRONMENT=Development dotnet tool run dotnet-ef database update --project src/backend/Libra.Infrastructure --startup-project src/backend/Libra.Api
  ```

- Automatic apply: when `Database:MigrateOnStartup` is `true` the API applies pending migrations at startup. It is `true` in Development and in integration tests, `false` everywhere else (D-020). Destructive migrations are never auto-applied in production.
- Current migrations: `InitialIdentity` (Phase 1), `AddFinanceCore` (Phase 2: the five finance tables, their
  indexes, check constraints, and foreign keys), `AddNutrition` and `AddFoodAnalysis` (Phase 3), `AddTasks`
  (Phase 4A), `AddSleep` (Phase 4B), `AddRecurringAndDebts` (Phase 3: `recurring_transactions`,
  `recurring_occurrences`, `debts`, `debt_movements`, generated as `20260915131248_AddRecurringAndDebts`).
- `AddSleep` is hand-augmented after generation, because EF Core models neither construct: it runs
  `CREATE EXTENSION IF NOT EXISTS btree_gist` and then adds `ex_sleep_sessions_no_overlap`, an
  `EXCLUDE USING gist (user_id WITH =, tstzrange(started_at_utc, ended_at_utc, '[)') WITH &&)` restricted to
  completed rows. Regenerating the migration would drop both; keep them when scaffolding over it.

## Test databases

Integration tests start a throw-away PostgreSQL container with Testcontainers per test collection, apply all migrations on startup, and configure the connection string in memory. Schema-level invariants are also asserted from the EF design-time model in `tests/Libra.UnitTests/Finance/FinanceSchemaTests.cs`.
